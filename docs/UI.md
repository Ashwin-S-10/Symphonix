# Symphonix UI/UX Guidelines

## Product feel
- Reference: Spotify's strong information hierarchy, persistent player, dense music browsing, and confident use of album art.
- Goal: a polished music product designed by a human product team—not a generic AI-generated dashboard.
- Personality: music-first, dark, tactile, editorial, fast, understated.
- Prioritize recognizable music-app patterns over novelty for novelty's sake.

## Visual direction
- Default to a dark theme with near-black/charcoal surfaces and one restrained accent color.
- Use album/cover art as the primary visual color; avoid rainbow gradients and excessive glow.
- Establish clear hierarchy: page title → section title → cover/title/artist → secondary metadata.
- Use consistent spacing, alignment, type scale, radii, and icon stroke weight.
- Use typography with character; avoid oversized generic headings on every screen.
- Use subtle borders and tonal surface changes instead of cards around every element.
- Reserve animation for playback, hover, navigation, and state transitions; keep it quick and purposeful.
- Design empty, loading, error, offline, and reconnecting states—not just the happy path.

## Layout principles
- Desktop: compact left navigation, central browsing area, persistent bottom player; optional right-side queue/space panel only when useful.
- Mobile: bottom navigation, compact player, responsive song rows, and a clear now-playing/space view.
- Keep primary playback controls visible and predictable.
- Keep space status, host identity, participant count, and sync state easy to find.
- Use song rows for dense lists and cover grids for discovery/group browsing.
- Group related demo songs into named collections; do not imply the groups were generated by ML in Phase 1.

## Music browsing
- Show cover art or intentional placeholders, track title, artist, and duration when available.
- Support play, pause, selection, and clear active/playing states.
- Use hover actions on desktop and visible accessible controls on touch devices.
- Avoid excessive metadata, badges, charts, and decorative metrics.
- Keep search and filters simple; only show controls that work.

## Space creation and synchronization
- Make “Create space” and “Join space” easy to discover.
- Give each space a clear state: creating, waiting, connecting, buffering, synchronized, reconnecting, or failed.
- Display participant names/devices and connection/readiness state without turning the page into a network-monitor dashboard.
- Explain whether the user is host or participant.
- Provide clear host controls: play, pause, seek, next track, and end space.
- Participants should understand that host playback controls shared playback.
- Show useful feedback for buffering, connection failure, and resynchronization.
- Avoid claiming perfect synchronization; communicate status honestly.

## Do
- Build reusable design tokens for color, typography, spacing, radii, elevation, and motion.
- Use a consistent icon family; prefer simple line icons.
- Use semantic HTML, keyboard navigation, visible focus states, accessible contrast, and labelled controls.
- Make controls work; avoid decorative/inert buttons.
- Provide responsive layouts and respect reduced-motion preferences.
- Use realistic music content and artwork; use consistent fallbacks if artwork is unavailable.
- Make loading and interaction states deliberate.
- Keep the player persistent across navigation where practical.

## Don't
- Don't use the default AI-generated landing-page formula: giant gradient hero, floating glass cards, random glowing orbs, and generic feature tiles.
- Don't make every section a rounded card.
- Don't use gradients/glassmorphism as the main design identity.
- Don't use oversized empty space that hides the music catalog.
- Don't add fake analytics, waveform visualizations, equalizer animations, ratings, or metrics that have no real function.
- Don't use emoji as primary UI icons.
- Don't invent album art, artist names, track durations, or user avatars as factual metadata.
- Don't show ML scores, clusters, or AI explanations in Phase 1.
- Don't expose networking internals (ICE candidates, SDP, raw packet states) to ordinary users.
- Don't rely on color alone to communicate connection or playback status.
- Don't autoplay audio unexpectedly or hide important playback controls on mobile.

## Suggested design tokens
- Background: near-black, e.g. `#121212`.
- Main surface: charcoal, e.g. `#181818`.
- Elevated surface: slightly lighter charcoal, e.g. `#242424`.
- Primary text: near-white.
- Secondary text: muted gray.
- Accent: one restrained green or another selected brand accent; use sparingly.
- Spacing: consistent 4/8 px base scale.
- Corners: modest radii; reserve pills for chips and compact controls.
- Motion: short transitions; no constant decorative animation.

## Phase 1 UI scope
- Home / demo library.
- Named collections grouping the 20 demo songs.
- Song list and playback controls.
- Create space / join space.
- Host and participant views.
- Participant list and connection/synchronization status.
- Persistent player and clear buffering/error states.
- No ML screens, recommendation pages, cluster visualizations, or personalization UI.

## Acceptance checklist
- [ ] Looks and behaves like a deliberate music product, not a generic dashboard.
- [ ] Catalog is visible quickly; no oversized hero blocks.
- [ ] Player controls are persistent and predictable.
- [ ] Song rows and cover grids have consistent alignment and spacing.
- [ ] Create/join space flows are obvious.
- [ ] Host/participant roles and sync state are understandable.
- [ ] Responsive and keyboard-accessible.
- [ ] No decorative/inert controls or fake data visualizations.
